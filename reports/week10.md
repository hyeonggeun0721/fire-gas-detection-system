# 10주차 보고서 — 타이머/카운터 기반 주기적 센싱 스케줄링

## 이번 주 목표

- Timer0을 CTC 모드로 설정해 5ms 주기 하드웨어 인터럽트 생성
- 기존 `_delay_ms(5)` 소프트웨어 지연 기반 루프 타이밍을 타이머 인터럽트 기반으로 교체
- 프리스케일러 계산 오류로 인한 주기 어긋남 재현 및 수정

## 구현 내용

- `timer0_init()`에서 `TCCR0`의 `WGM01` 비트로 CTC(Clear Timer on Compare Match)
  모드를 설정하고, `TIMSK`의 `OCIE0` 비트로 비교 일치 인터럽트를 활성화했다.
- `ISR(TIMER0_COMP_vect)`는 `tick_flag`만 세팅하는 최소한의 작업만 수행한다
  (9단계에서 익힌 "ISR은 가볍게" 원칙을 재사용).
- 메인 루프 마지막의 `_delay_ms(5)`를 제거하고, `tick_flag`가 설정될 때까지
  대기한 뒤 리셋하는 방식으로 바꿔 루프 주기를 타이머가 결정하도록 했다.
  이는 11단계 이후 서보 PWM, 13단계 UART 등 타이밍이 중요한 기능을 추가할 때
  소프트웨어 지연 누적으로 인한 오차를 줄이기 위한 선행 작업이다.
- `TIMER0_OCR` 매크로로 목표 주기(200Hz = 5ms)에 필요한 비교값을
  `F_CPU / TIMER0_PRESCALER / TIMER0_TARGET_HZ - 1`로 계산한다.

## 발생한 오류 및 트러블슈팅 과정

**증상**: 프리스케일러를 64로 설정하고 빌드하자, avr-gcc가 다음 경고를 출력했다.

```
main.c: In function 'timer0_init':
main.c:52:20: warning: conversion from 'long unsigned int' to 'uint8_t' {aka
'volatile unsigned char'} changes value from '1249' to '225' [-Woverflow]
   52 | #define TIMER0_OCR (F_CPU / TIMER0_PRESCALER / TIMER0_TARGET_HZ - 1)
      |                    ^
main.c:88:12: note: in expansion of macro 'TIMER0_OCR'
   88 |     OCR0 = TIMER0_OCR;
```

**원인 분석**: 목표 주기 5ms(200Hz)를 만들기 위해 필요한 카운트 값은
`16,000,000 / 64 / 200 - 1 = 1249`인데, `OCR0`은 8비트 레지스터라 0~255
범위만 표현할 수 있다. 1249를 8비트에 대입하면 하위 8비트만 남아 225가
저장된다. 그 결과 실제 타이머 주기는 `(225+1) * 64 / 16,000,000 ≈ 0.904ms`로,
목표(5ms)보다 약 5.5배 빠르게 인터럽트가 발생하게 된다.

이 오차는 단순히 "루프가 좀 더 빨리 돈다"는 수준을 넘어, 5단계에서 구현한
디바운싱 로직(`DEBOUNCE_THRESHOLD=4`, "4 × 5ms = 20ms"라는 전제로 값을 정함)에도
영향을 미친다. 실제 주기가 0.904ms라면 디바운싱 시간은 `4 × 0.904ms ≈ 3.6ms`로
단축되어, 원래 의도했던 20ms보다 훨씬 짧아지고 디바운싱 효과가 크게
약화된다. 이처럼 한 모듈(타이머)의 설정 오류가 이미 검증됐던 다른 모듈
(디바운싱)의 전제를 깨뜨릴 수 있다는 점이 이번 오류의 중요한 교훈이다.

**해결 과정**:
1. avr-gcc의 `-Woverflow` 경고에서 정확한 원인(1249 → 225 절삭)을 바로 확인했다.
2. 목표 주기 5ms를 8비트 타이머로 만들 수 있는 프리스케일러 값을 역산했다:
   `16,000,000 / 1024 / 200 - 1 = 77`로, 255 이내에 들어온다.
3. `TIMER0_PRESCALER`를 1024로, `TCCR0`의 `CS02:00`을 `111`(분주비 1024)로 수정했다.
4. 재빌드 결과 경고가 사라졌고, `avr-objdump -d main.elf`로 `ldi r24, 0x4D ; 77`
   명령을 확인해 `OCR0`에 정확히 77이 로드됨을 검증했다.
5. `tests/test_timer_prescaler.c` 호스트 테스트를 추가해, 동일한 계산식으로
   프리스케일러 64(버그)에서는 실제 주기가 904us(목표 대비 약 82% 오차)가 되고,
   프리스케일러 1024(수정)에서는 4992us(오차 0.16%)가 됨을 회귀 테스트로 고정했다.

```
$ make test
...
목표 주기: 5000 us
[프리스케일러 64]  필요 OCR0=1249 -> 8비트 저장값=225 -> 실제 주기=904.0 us
[프리스케일러 1024] 필요 OCR0=77 -> 8비트 저장값=77 -> 실제 주기=4992.0 us
PASS
```

## 시뮬레이션 검증 결과

**확인해야 할 시뮬레이션 시나리오** (Proteus/SimulIDE):
1. `main.hex`(수정 후, `5554b2c` 커밋)를 로드해 실행한다.
2. 로직 분석기(또는 오실로스코프 도구)로 타이머 관련 핀이나 디버그 토글 핀의 주기를 측정해 약 5ms에 근접하는지 확인한다(직접 관측 가능한 핀이 없다면, 테스트 버튼을 눌렀을 때 반응 체감 속도가 이전 주차와 크게 달라지지 않는지로 간접 확인).
3. 수정 전(`e0b5b2e` 커밋)과 비교해, 버튼 반응이 비정상적으로 빠르거나(디바운싱 시간 단축) 부저/LCD 갱신이 과도하게 빈번한지 확인한다.

> 위 시나리오는 아직 사용자 확인 전입니다. 직접 실행하신 결과를 알려주시면 이 절을 업데이트하겠습니다.
> (프리스케일러/OCR0 계산 자체는 avr-gcc 경고, avr-objdump, 호스트 회귀 테스트로 다각도로 결정적 검증을 완료했습니다.)
