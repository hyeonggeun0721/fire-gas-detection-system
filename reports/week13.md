# 13주차 보고서 — UART 통신(PC 관제실로 신고 메시지 전송)

## 이번 주 목표

- USART0(TXD0=PE1)로 PC 관제실에 상태 알림 메시지 전송
- 경보/대피 상태 진입 시 UART 메시지 전송 연결
- 보드레이트 불일치로 인한 통신 깨짐 재현 및 수정

## 구현 내용

- `firmware/uart.h`/`uart.c`: `UBRR0H`/`UBRR0L`에 보드레이트 분주값을
  설정하고, `UCSR0B`의 `TXEN0`으로 송신을 활성화, `UCSR0C`를 8비트 데이터/
  패리티 없음/정지비트 1(8N1)로 구성했다. `uart_putc()`는 송신 버퍼가 빌 때까지
  (`UDRE0` 플래그) 대기한 뒤 `UDR0`에 값을 쓰는 블로킹 방식이다.
- `main.c`의 `show_state()`에서 `FIRE_STATE_ALARM`/`FIRE_STATE_EVACUATE` 진입 시
  각각 `uart_puts()`로 관제실 알림 메시지를 전송하도록 연결했다.
- **설계 상 참고**: 6단계에서는 LCD의 HD44780 폰트 ROM이 한글을 지원하지
  않아 영문 문구를 썼지만, UART는 단순히 바이트를 전송할 뿐이고 PC 쪽
  터미널 프로그램이 UTF-8을 그대로 표시할 수 있으므로 관제실 메시지는
  한글로 작성했다("[경보] 가스 또는 온도 임계값 초과, 혹은 불꽃 감지",
  "[대피] 화재 확정, 비상구 개방 - 즉시 대피 바랍니다"). 동일한 "문자를
  표시/전송한다"는 요구사항이라도 출력 장치의 제약에 따라 구현 방식이
  달라진다는 점을 확인할 수 있었다.

## 발생한 오류 및 트러블슈팅 과정

**증상**: 초기 구현에서 `UART_UBRR`을 51로 하드코딩했다. 이는 F_CPU=8MHz
클럭을 가정한 예제 코드에서 9600bps를 내기 위한 값을 그대로 가져온
것이었다. 이 프로젝트는 2단계 아키텍처 설계상 F_CPU=16MHz이므로, 같은 UBRR
값이라도 실제 보드레이트는 달라진다. 호스트 단위 테스트
(`tests/test_uart_baud.c`)로 실제 만들어지는 보드레이트를 역산했다.

```
$ make test
...
목표 보드레이트: 9600 bps (F_CPU=16000000 Hz)
[버그] UBRR=51  -> 실제 19230.8 bps (오차 100.3%)
[수정] UBRR=103 -> 실제 9615.4 bps (오차 0.16%)
```

실제 만들어지는 보드레이트가 목표(9600bps)의 약 2배(19230.8bps)에 달했다.
UART는 송신 측과 수신 측이 사전에 합의한 동일한 보드레이트로 비트를
샘플링해야 하는데, 이 정도 오차(2~3%를 훨씬 초과)에서는 수신 측(PC
터미널)이 비트 경계를 완전히 놓쳐 프레이밍 오류가 발생하고, 화면에는
깨진 문자가 표시되거나 아무것도 표시되지 않게 된다.

**원인 분석**: 인터넷의 UART 예제 코드는 흔히 특정 클럭(8MHz 등)을 가정하고
UBRR 값을 미리 계산해 상수로 제시한다. 이 상수를 프로젝트의 실제 클럭
설정을 확인하지 않고 그대로 복사해 쓴 것이 원인이다. 흥미롭게도 이 프로젝트에서
"코드가 가정하는 클럭"과 "실제 보드의 클럭"이 어긋나는 문제는 이번이
처음이 아니다: 3단계(Makefile의 MCU 오타로 인한 빌드 실패)와 10단계(타이머
프리스케일러 계산 오류로 인한 주기 어긋남)에 이어, 이번에도 같은 종류의
"클럭 가정 불일치"가 다른 형태(보드레이트)로 반복해서 나타난 것이다.

**해결 과정**:
1. UBRR과 실제 보드레이트, F_CPU의 관계식(`baud = F_CPU / (16 * (UBRR+1))`)을 확인했다.
2. `UART_UBRR`을 하드코딩된 51 대신 `(F_CPU / 16 / UART_BAUD) - 1` 매크로로
   계산하도록 수정했다(`UART_BAUD=9600`, 요구사항 명세서 6절 기본값).
3. `avr-objdump -d main.elf`로 `ldi r24, 0x67 ; 103`이 `UBRR0L`에 로드되는
   것을 확인했다(16,000,000/16/9600 - 1 = 103).
4. `tests/test_uart_baud.c`를 재실행해 실제 보드레이트가 9615.4bps(오차
   0.16%, 통상 허용 범위인 2~3% 이내)로 목표에 근접함을 확인했다.

## 시뮬레이션 검증 결과

**확인해야 할 시뮬레이션 시나리오** (Proteus/SimulIDE):
1. PE1(TXD0)을 시뮬레이터의 가상 터미널(또는 UART 모니터 컴포넌트)에 9600bps, 8N1로 연결한다.
2. 수정 전(`91466d1` 커밋) `.hex`를 로드해 실행하고, 테스트 버튼이나 온도/가스 값을 조작해 경보 상태에 진입시켰을 때 터미널에 깨진 문자(모지바케)가 표시되거나 아무것도 표시되지 않는지 확인한다.
3. 수정 후(`712d6ae` 커밋) `.hex`를 로드해 실행하고, 경보 상태 진입 시 터미널에 `[경보] 가스 또는 온도 임계값 초과, 혹은 불꽃 감지` 메시지가 정상적으로 표시되는지 확인한다.
4. 대피 상태로도 진입시켜 `[대피] 화재 확정, 비상구 개방 - 즉시 대피 바랍니다` 메시지가 표시되는지 확인한다.

> 위 시나리오는 아직 사용자 확인 전입니다. 직접 실행하신 결과를 알려주시면 이 절을 업데이트하겠습니다.
> (UBRR과 실제 보드레이트 계산 자체는 avr-objdump와 호스트 단위 테스트로 결정적으로 검증 완료했습니다.)
