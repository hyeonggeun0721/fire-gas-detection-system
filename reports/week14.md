# 14주차 보고서 — 통합 테스트 및 시나리오별 시뮬레이션 검증

## 이번 주 목표

- 지금까지 통합된 시스템(GPIO/LCD/ADC/인터럽트/타이머/PWM/UART)을 검토해
  여러 모듈이 동시에 동작할 때 생기는 충돌/타이밍 문제를 찾아 수정
- 3~13단계 보고서에 흩어져 있던 "사용자 확인 대기" 시뮬레이션 시나리오를
  하나의 통합 테스트 체크리스트로 정리

## 구현 내용

- `main.c`를 처음부터 끝까지 다시 읽으며 각 모듈이 서로에게 미치는 영향을
  검토했다. 그 결과 `show_state()`의 부저 재생 방식(`beep()`)이 실질적인
  타이밍 문제를 일으키고 있음을 발견했다(아래 "발생한 오류" 참조).
- `firmware/buzzer_seq.c`: 부저 삑삑 패턴을 상태 기계로 표현한 순수 로직
  (`buzzer_seq_start()`, `buzzer_seq_tick()`)을 하드웨어 레지스터 없이
  구현했다. 호스트 환경에서 단위 테스트가 가능하다.
- `firmware/buzzer.c`: `buzzer_seq.c`를 감싸 실제 `PORTD`(부저 핀)를
  제어하는 얇은 하드웨어 래퍼로 구성했다(`buzzer_init/start/tick`).
- `main.c`의 메인 루프에서 매 5ms 틱마다 `buzzer_tick()`을 한 번씩 호출해,
  부저 패턴이 메인 루프를 막지 않고 배경에서 재생되도록 했다.
- `docs/test-scenarios.md`: 8개의 종단간(end-to-end) 시나리오(A~H)로
  통합 테스트 체크리스트를 작성했다. 특히 시나리오 H는 이번 주 수정한
  부저 blocking 문제가 실제로 해결됐는지를 직접 확인하는 시나리오다.

## 발생한 오류 및 트러블슈팅 과정

**증상(통합 검토로 발견)**: `show_state()`의 `beep(count)` 함수는
`_delay_ms(100)`을 `count`회 반복 호출하는 완전한 블로킹 함수였다. 대피
상태는 `beep(3)`을 호출하므로, 상태 전이 한 번에 `(100+100)ms × 3 =
600ms` 동안 `main()`의 무한 루프 전체가 멈춘다. 이 시스템은 12단계에서
매 5ms 틱마다 센서를 다시 읽고 상태를 재평가하도록 설계했는데, 부저가
울리는 600ms 동안은 이 재평가도, 13단계에서 추가한 UART 전송 판단도,
테스트 버튼 반응도 전혀 진행되지 않는다.

이 문제는 어느 한 주차의 코드가 "틀려서" 생긴 것이 아니라, 각 주차마다
개별적으로는 올바르게 동작하던 기능들(4단계의 GPIO 부저 제어, 12단계의
매 틱 재평가 루프)을 한데 모았을 때 비로소 드러나는 **통합 문제**였다.
화재는 시간이 지날수록 악화될 수 있으므로, 상태가 바뀔 때마다 최대
600ms씩 센서 재평가가 지연되는 것은 이 시스템의 목적(신속한 화재 대응)에
비추어 볼 때 실질적으로 개선이 필요한 문제로 판단했다.

**원인 분석**: LED나 서보처럼 레지스터에 값을 쓰고 즉시 반환되는 출력과
달리, 부저의 "삑삑" 패턴은 본질적으로 시간이 걸리는 동작이다. 이를
`_delay_ms()`로 구현하면 그 시간 동안 CPU가 다른 어떤 작업도 할 수 없다.
센서 읽기, 상태 판단, 버튼 응답이 모두 같은 메인 루프 안에서 순차
실행되는 이 시스템의 구조상, 한 기능(부저)의 블로킹 호출이 전체 시스템의
응답성에 직접 영향을 준다는 점을 통합 검토 전에는 놓치고 있었다.

**해결 과정**:
1. `buzzer_seq.c`에 순수 논블로킹 시퀀서(`buzzer_seq_tick()`)를 작성했다.
   호출될 때마다 5ms만큼 상태를 진행시키고 즉시(O(1)) 반환한다.
2. 호스트 단위 테스트(`tests/test_buzzer_seq.c`)를 작성해 `beep_count`별로
   총 ON 틱 수가 예상(`beep_count × 20틱 = beep_count × 100ms`)과 일치하는지
   검증했다. **이 테스트가 커밋 전에 실제로 버그를 하나 더 잡아냈다**:
   처음 작성한 로직은 OFF→ON 전환 호출이 `ticks_left`를 소비하지 않은 채
   ON 신호를 반환해, 두 번째 이후 삑 소리가 매번 1틱씩 길어지는 자체
   오프바이원 버그가 있었다.
   ```
   $ make test
   ...
   beep_count=1 -> 총 21틱 진행, ON 틱 20개 (기대값 20)
   beep_count=2 -> 총 63틱 진행, ON 틱 41개 (기대값 40)
   FAIL: beep_count=2에서 ON 틱 수가 예상과 다름
   ```
   전환 호출이 상태만 준비하고 0을 반환하도록 수정한 뒤 재검증하니 모든
   `beep_count`에서 기대값과 정확히 일치했다.
   ```
   beep_count=1 -> 총 21틱 진행, ON 틱 20개 (기대값 20)
   beep_count=2 -> 총 63틱 진행, ON 틱 40개 (기대값 40)
   beep_count=3 -> 총 105틱 진행, ON 틱 60개 (기대값 60)
   PASS
   ```
3. `main.c`에서 `beep()`과 관련 `_delay_ms` 호출을 모두 제거하고,
   `buzzer_start()`(상태 진입 시 1회)와 `buzzer_tick()`(매 틱 1회)으로
   교체했다. 재빌드 결과 정상적으로 빌드되었다.

## 알려진 잔여 한계

`show_state()`가 LCD를 갱신하는 데도 약 5~8ms(문자 출력 + 지우기 지연)가
걸려 여전히 소폭의 블로킹이 남아있다. 부저(최대 600ms)에 비하면 훨씬
작고, 상태가 실제로 바뀔 때만 한 번 호출되므로 이번 단계에서는 우선순위가
낮다고 판단해 수정하지 않았다. 필요하다면 15단계 최종 최적화에서 추가
검토할 수 있다.
