# 12주차 보고서 — 화재 판단 알고리즘 및 상태 기계 설계

## 이번 주 목표

- 온도/가스/불꽃 센서 값을 종합해 정상/주의/경보/대피 4단계 상태 기계로 통합
- 상태 전이 조건 누락 재현 및 수정

## 구현 내용

- `firmware/fire_logic.h`/`fire_logic.c`: 요구사항 명세서(`docs/requirements.md`
  5절)의 상태 정의를 그대로 구현했다. `fire_evaluate(prev_state, temp_c, gas_pct,
  flame_detected, &alarm_ticks)`가 매 틱 호출되어 다음 상태를 반환한다.
  - 정상: 온도/가스 모두 임계값 이하
  - 주의: 온도(`TEMP_WARNING_C=40`) 초과, 가스/불꽃 없음
  - 경보: 가스(`GAS_ALARM_PERCENT=50`) 초과 또는 불꽃 감지
  - 대피: 경보 상태가 `ALARM_TO_EVACUATE_TICKS`(600틱 = 5ms×600 ≈ 3초) 지속되거나,
    온도·가스가 동시에 임계값을 초과하면 즉시 격상
  - AVR 레지스터에 의존하지 않는 순수 함수라 호스트에서 단위 테스트가 가능하다.
- `main.c`를 매 5ms 틱마다 온도(ADC0)/가스(ADC1)를 읽고 `flame_detected` 플래그와
  함께 `fire_evaluate()`에 전달해 상태를 자동 갱신하는 구조로 재작성했다.
  이전까지 버튼으로 수동 순환하던 방식에서, 이제 버튼은 "강제로 정상 상태로
  리셋"하는 테스트/리셋 용도로 의미가 바뀌었다(요구사항 명세서 3절에서 정의한
  본래 목적과 일치).
- LED는 2단계에서 확정한 하드웨어 예산(3개, PA0-2)상 경보와 대피가 같은
  `LED_ALARM`(빨강)을 공유한다. 대신 LCD 문구(`!! ALARM !! / Stand by` vs
  `!! EVACUATE !! / EXIT NOW`)와 부저 패턴(경보 1회 삑, 대피 3회 삑),
  서보 개폐(경보는 닫힘 유지, 대피에서만 개방)로 두 상태를 구분했다.
- `show_state()`는 상태가 실제로 바뀔 때만 호출되도록 했다(9단계에서 배운
  "불필요한 반복 갱신 방지" 교훈을 반영).

## 발생한 오류 및 트러블슈팅 과정

**증상**: 빌드 시 avr-gcc가 다음 경고를 출력했다.

```
firmware/fire_logic.c:4:36: warning: unused parameter 'flame_detected' [-Wunused-parameter]
```

`flame_detected` 매개변수가 함수 안에서 전혀 사용되지 않는다는 신호였다.
이를 호스트 단위 테스트(`tests/test_fire_logic.c`)로 재현했다: 불꽃이
감지됐지만(`flame_detected=1`) 온도(25°C)와 가스(10%)는 모두 정상 범위인
시나리오를 실제 `fire_logic.c`에 대해 실행했다.

```
$ make test  (수정 전 fire_logic.c 기준)
...
[시나리오1] 불꽃 감지, temp=25C, gas=10% -> 버그: NORMAL, 수정: NORMAL (기대값: ALARM)
FAIL: 수정 로직에서 불꽃 감지가 경보로 이어지지 않음
```

요구사항 명세서 5절은 "가스 임계값 초과 **또는** 불꽃 감지" 중 하나만
만족해도 경보로 정의하는데, 실제로는 온도/가스가 낮으면 불꽃이 감지돼도
정상 상태로 남는 것으로 확인됐다.

**원인 분석**: 9단계에서는 `ISR(INT0_vect)`가 세팅한 `flame_detected` 플래그를
메인 루프가 직접 검사해 `STATE_ALARM`으로 전환시켰다(그 자체로 9단계의
플래그 리셋 버그를 겪고 고쳤던 로직). 그런데 12단계에서 온도/가스/불꽃 판단을
모두 `fire_evaluate()` 하나로 통합하는 리팩터링을 하면서, 이 불꽃 조건을 새
함수로 옮겨 적는 것을 빠뜨렸다. 결과적으로 **9단계에서 이미 해결했던 "불꽃
감지가 무시되는" 문제가 통합 과정에서 다시 나타난 회귀(regression) 버그**였다.
개별 기능이 각각 올바르게 동작하더라도, 여러 기능을 하나의 로직으로 통합하는
과정에서 기존 조건이 누락될 수 있다는 점을 보여주는 사례다.

**해결 과정**:
1. avr-gcc의 `-Wunused-parameter` 경고로 `flame_detected`가 로직에 전혀
   반영되지 않고 있음을 먼저 포착했다.
2. `tests/test_fire_logic.c`의 시나리오1로 실제 `fire_logic.c`에 대해 문제를
   재현/확정했다.
3. 경보 판단 조건을 `if (gas_high)`에서 `if (gas_high || flame_detected)`로 수정했다.
4. 재빌드 결과 unused parameter 경고가 사라졌고, `make test`의 4개
   시나리오(불꽃 단독 감지, 가스 단독 초과, 온도+가스 동시 초과 시 즉시
   대피 격상, 경보 장시간 지속 시 대피 격상)가 모두 PASS함을 확인했다.

```
$ make test  (수정 후)
...
[시나리오1] 불꽃 감지, temp=25C, gas=10% -> 버그: NORMAL, 수정: ALARM (기대값: ALARM)
[시나리오2] gas=60% 단독 -> 수정: ALARM (기대값: ALARM)
[시나리오3] temp=45C(>=40) & gas=60%(>=50) 동시 -> 수정: EVACUATE (기대값: EVACUATE)
[시나리오4] gas=60% 상태를 600틱 지속 -> 수정: EVACUATE (기대값: EVACUATE)
PASS
```

## 시뮬레이션 검증 결과

**확인해야 할 시뮬레이션 시나리오** (Proteus/SimulIDE):
1. PF0/PF1에 온도/가스를 모사하는 가변저항을, PD0에 불꽃 센서(스위치)를 연결한다.
2. `main.hex`(수정 후, `52e9b84` 커밋)를 로드해 실행한다.
3. 온도/가스를 정상 범위로 두고 PD0 스위치만 눌러(불꽃 감지) LCD가 즉시 `!! ALARM !!`으로 바뀌는지 확인한다.
4. 온도를 40°C 이상, 가스를 50% 이상으로 동시에 올려 즉시 `!! EVACUATE !!`로 바뀌고 서보가 열리는지 확인한다.
5. 가스만 50% 이상으로 유지한 채 약 3초 이상 기다려 경보에서 대피로 자동 격상되는지 확인한다.
6. 테스트 버튼을 눌러 정상 상태로 강제 복귀되는지 확인한다.

> 위 시나리오는 아직 사용자 확인 전입니다. 직접 실행하신 결과를 알려주시면 이 절을 업데이트하겠습니다.
> (상태 전이 규칙 자체는 호스트 단위 테스트로 결정적으로 검증 완료했습니다.)
